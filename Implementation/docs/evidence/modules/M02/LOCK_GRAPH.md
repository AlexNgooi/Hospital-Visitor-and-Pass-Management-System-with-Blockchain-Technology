# M02 locking and M03 integration port

All domain transactions use the reviewed M00 capabilities prefix. Discovery reads identify immutable owner/counter/display/context IDs without locks. After the prefix, operations lock displays in sorted ID order, then the current anonymous context, then challenges, then grants. The pointer/version is re-read after locks; a changed pointer returns a safe conflict and rolls back. Never chase a new display/owner while already holding later locks.

| Operation | Locks after discovery |
|---|---|
| Create display | M00 sorted user/counter/binding/owner prefix, then insert display |
| Current challenge | Prefix, display, select/insert its unique slot challenge |
| First/repeated exchange | Prefix for new source and any live old source plus anonymous binding, sorted displays, unique context insert/context lock, incoming challenge, old grant, replacement insert/pointer CAS |
| GET current grant / M03 lockGrant | Prefix including anonymous binding and original source, display, context/pointer comparison, current grant |
| Revoke display | Prefix, display, sorted affected contexts, sorted challenges, sorted grants; clears only matching pointers and preserves consumed grants |
| Permission/logout | M00 prefix before epoch invalidation; M02 guards reject it at next use, without framework saves inside domain transactions |

The complete prefix is identity policy where applicable → sorted users → sorted counters → permissions when mutating → sorted bindings → sorted auth contexts → sorted displays → entry contexts → challenges → grants → registration/idempotency → audit. M00 performs actual framework-session metadata checks without framework/domain reverse locking. Public traffic never renews the original staff owner, even when the same browser has a staff cookie. Owner expiry, logout, account/counter permission changes and explicit revocation all prevent pending grant use.

M03 must resolve `anonymous(bindingId)` outside its domain transaction, producing the stable anonymous scope for idempotency. An actual servlet/framework binding is required; a public reference never reconstructs authority. In one outer READ_COMMITTED transaction, check successful replay using the reviewed scope/operation/key/body encoding first, then call `lockGrant(bindingId, originalFormContext)` for a new command. Use `GrantAccess.scope()` as the source of counter/environment/category restriction; validate the selected visitor category against this scope and M03's current field whitelist. Write the registration, call `consume(access, registrationId)`, append local audit and record the successful safe idempotency response in that same transaction, following the global order. Any failure rolls everything back.

`GrantAccess` has a private constructor and is bound to a unique TransactionSynchronization marker. Consumption requires both the exact receipt resource and that marker's identity in the current transaction's synchronization list. Arbitrary thread resources alone survive REQUIRES_NEW suspension and are insufficient. A suspended outer receipt is therefore rejected before any SQL read/mutation in an inner transaction; after resumption the outer receipt remains usable. Completion cleans up the resource, and consumption unbinds it to prevent reuse. The receipt cannot be fabricated, serialized as authorization or reused in a later transaction. `consume` also requires current deadline/state and exact binding/context, updates one grant and clears/increments its matching pointer. No nested independent consumption transaction is permitted. Revalidate anonymous authority before even successful replay; an expired/deleted anonymous session cannot resurrect a result. Same-scope successful safe replay may survive consumed/expired/revoked grant within M00's 24h retention; a new command may not.

Frontend `RegistrationEntry` optionally renders a future M03 child using the exact accepted EntryGrant. Its keyed disabled fieldset preserves input on temporary failure and resets only after confirmed replacement/explicit adopted context. M03 still captures that original context in schema/MRN/submission and request hash, validates server errors, and must not GET a new context to rebind old input. No M03 field/schema/API implementation is included.

Real MySQL races cover first insert, duplicate confirmation, replace versus consume, exchange versus revoke, revoke versus consume, permission/logout versus exchange. The synthetic consumer proves rollback and exactly-once grant transitions, including actual SQL audit failure and safe idempotency replay; it does not prove the unimplemented M03 aggregate.
